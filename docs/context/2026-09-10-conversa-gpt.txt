Quero usar este chat exclusivamente como acompanhamento estratégico e técnico do desenvolvimento do projeto Meu Visto Fácil no Codex.

Contexto geral

O Meu Visto Fácil será reconstruído do absoluto zero.

Não vamos reaproveitar código do projeto antigo. Vamos reaproveitar apenas a ideia central do TCC original: uma plataforma para ajudar pessoas a entender caminhos de imigração, com foco em informações organizadas, fontes oficiais, checklists personalizados e uso controlado de IA.

O principal objetivo atual é transformar o Meu Visto Fácil em um projeto forte de portfólio.

Precisamos chegar a:

- aplicação funcional;
- publicada na Vercel;
- código organizado no GitHub;
- arquitetura profissional;
- boa interface;
- autenticação;
- banco de dados;
- backend real;
- IA;
- testes;
- segurança;
- documentação;
- README profissional;
- screenshots e case study.

A intenção é que o projeto demonstre competências de Full Stack, principalmente:

COMO ESTAMOS TRABALHANDO
==================================================

Eu estou desenvolvendo o projeto usando o Codex App.

Este chat não deve programar o projeto diretamente.

O papel deste chat é funcionar como uma espécie de Tech Lead / Arquiteto / guia de uso do Codex.

Fluxo:

Eu digo:
"vamos para a próxima fase"

Este chat:
1. identifica onde estamos no roadmap;
2. explica brevemente o objetivo da fase;
3. prepara um prompt bem estruturado para eu colar em uma nova thread do Codex;
4. recomenda o nível de reasoning adequado;
5. espera eu executar;
6. eu volto com resultado, dúvida ou problema;
7. analisamos juntos;
8. somente após minha aprovação avançamos para a próxima fase.

NÃO avançar automaticamente de fase.

Sempre fazemos uma fase de cada vez.

Não quero receber várias fases de implementação ao mesmo tempo.

3. ARCHITECTURE.md

Direção arquitetural principal:

UI
↓
Application
↓
Domain
↓
Infrastructure

Frontend e backend estão no mesmo projeto Next.js, mas as responsabilidades são separadas.

Princípios:

- Server Components por padrão;
- Client Components somente quando necessário;
- business logic fora de componentes;
- Route Handlers e Server Actions são boundaries, não lugares para colocar todo o domínio;
- Prisma deve ficar restrito à infraestrutura quando fizer sentido;
- Application Services coordenam operações;
- domínio deve ser testável;
- integrações externas devem ser encapsuladas;
- DTOs podem ser usados nas fronteiras;
- erros devem possuir códigos estáveis;
- logs estruturados;
- autorização sempre server-side;
- evitar internal HTTP calls desnecessárias;
- evitar overengineering.

Estrutura conceitual:

src/
├── app/
├── components/
├── features/
├── lib/
├── shared/
└── test/

Features planejadas:

- auth;

6. SECURITY.md

Princípios:

- Least Privilege;
- Server-Side Trust;
- Zero Trust for Input;
- Fail Closed;
- minimização de dados;
- defense in depth.

Autenticação:
Supabase Auth.

Autorização:
sempre server-side.

Nunca confiar em:

userId
ownerId
authUserId

vindos do browser.

Proteção contra IDOR.

Input validation com Zod.

Não fazer mass assignment.

Secrets apenas server-side.

Não expor:

OPENAI_API_KEY
DATABASE_URL
service-role keys
tokens

Importante:

o projeto valida URLs externas, então SSRF é uma ameaça importante.

A validação deve considerar:

- HTTPS;
- allowlist de hostname;
- correspondência segura de hostname;
- bloqueio de localhost/private IP;
- redirect validation;
- limite de redirects;
- timeout;
- portas;
- credentials em URL;
- response size;
- protocolos proibidos.

Também definimos regras para:

- XSS;
- CSRF;
- rate limiting;
- logging;
- CORS;
- headers;
- open redirect;
- host headers;
- personal data;
- LGPD/GDPR awareness;
- account deletion;
- dependency security;
- CI security.

↓

Ela classifica tarefas:

Security Review é obrigatório para:

- auth;
- authorization;
- ownership;
- AI endpoints;
- private user data;
- server-side URL fetching;
- account deletion;
- secrets;
- rate limits;
- privileged integrations.

Ela possui gates.

Se existe decisão de produto/arquitetura realmente importante:

PARA e pergunta ao usuário.

Se é uma decisão técnica pequena:

resolve sozinha.

Se testes falharem:

corrige e retesta.

Se Code Review encontrar CRITICAL/HIGH:

corrige
→ retesta
→ revisa novamente.

Se Security Review encontrar CRITICAL/HIGH:

corrige
→ security tests
→ security review novamente.

Evitar loops infinitos.

Após duas tentativas sem resolver, parar e reportar.

Status final:

READY
READY_WITH_MINOR_FINDINGS
BLOCKED

==================================================
OTIMIZAÇÃO DO CODEX
==================================================

Queremos aproveitar o Codex Pro sem desperdiçar contexto/uso.

Regras:

Durante desenvolvimento:
usar verificações direcionadas.

Exemplo:

alterou domain:
rodar testes daquela área.

alterou UI:
component tests + typecheck quando necessário.

database:
repository/integration tests.

AI:
AI tests relevantes.

Não rodar:

lint
typecheck
todos testes
build
E2E

depois de cada pequena alteração.

A verificação completa acontece principalmente no Final Gate.

Final Verification para feature significativa:

pnpm lint
pnpm typecheck
pnpm test
pnpm build

e:

pnpm test:e2e

quando necessário.

Code Review:

começa pelo diff.

Security Review:

começa pelo diff sensível.

Só expande para arquivos externos quando necessário.
